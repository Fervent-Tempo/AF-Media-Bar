## 一、内存优化工具

### 1. 指标必须先区分

- **工作集**：进程当前驻留物理内存的可分页页面。移出工作集后，页面可能仍在 RAM 中等待复用；再次访问可能发生软缺页，也可能需要从后备存储读回，不能一概称为硬缺页。
- **进程私有提交**：进程私有内存的提交需求。压低工作集不会自动释放仍然存活的私有对象，不能据此认定内存泄漏已经修复。
- **托管堆**：CLR 管理的对象内存。GC 只处理托管对象，不能替代各自所有者释放 COM、位图、窗口、订阅和其他原生资源。
- **待机页和文件缓存**：Windows 可复用的缓存资源。清空后空闲页可能增加，但后续应用还可能重新读取、建立缓存；可用内存变化不等于应用自身减少了提交。

上述判断以 [Microsoft 工作集与缺页说明](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)为依据。RAMMap 的类型、进程及待机优先级视图适合辅助定位内存去了哪里，不必把它的完整分析界面复制到媒体栏。

### 2. Mem Reduct 的实际机制

[清理实现](https://github.com/henrypp/memreduct/blob/04402de8b6a8ff9d1c5517c675d87c346655323c/src/main.c)包含系统工作集、系统文件缓存、修改页、全部待机页、低优先级待机页、注册表缓存、页面合并等分项，并可刷写卷缓存。其中多个操作通过 `NtSetSystemInformation` 及不同信息类执行；它们不能因为都叫 Native API 就视为具有同样稳定的公开兼容契约。

自动触发同时支持占用阈值和时间间隔；占用一直较高时仍有冷却判断，避免每次采样都执行。源码也读取清理前后指标、保存最后清理时间并可输出结果。适合借鉴的是分项、冷却及结果语义，而不是原样承诺其 README 中的下降比例。

| 操作方向 | 可能观察到的变化 | 代价及边界 | 本项目建议 |
|---|---|---|---|
| 仅 AF 缓存与托管对象 | 可重建资源及部分提交下降 | 清理后需要懒恢复；仍被使用的对象不可清除 | 复用现有所有者和剪枝协调器 |
| 进程工作集回收 | 驻留物理页减少 | 不修复存活对象占用；下次访问增加缺页 | 自身保留手动深度入口，不扩展为默认全进程清理 |
| 低优先级待机页 | 最低优先级缓存减少 | 仍属系统缓存，接口与权限需核对 | 系统实验首批候选，先手动且默认关闭 |
| 全部待机页、系统文件缓存 | 空闲页增加、缓存减少 | 影响其他应用缓存命中，收益依赖负载 | 不作为默认组合，单独实机对照后决定 |
| 修改页、卷缓存刷写 | 待写入内容处理后分类变化 | 可能增加磁盘 I/O 和耗时 | 首批排除 |
| 注册表缓存、页面合并等 | 系统特定内存结构变化 | 系统版本差异与维护成本更高 | 暂不规划 |

没有一个清理组合能保证改善播放、游戏或交互延迟。若原问题是泄漏，应先找持有者，不能用周期清空驻留页掩盖。

### 3. Windows Memory Cleaner 的补充价值

[功能说明](https://github.com/IgorMundstein/WinMemoryCleaner/blob/a19f25719c9b9a58a0acea99cb8adb4737d2d318/README.md)列出定时/压力触发、进程排除、快捷键、紧凑模式及清理反馈。对 AF 有价值的是执行范围可见、排除名单与明确结果，不是再建立一个独立的常驻监控界面。

[原生接口声明](https://github.com/IgorMundstein/WinMemoryCleaner/blob/a19f25719c9b9a58a0acea99cb8adb4737d2d318/src/Interop/NativeMethods.cs)同时包含公开的工作集、文件缓存接口以及 `NtSetSystemInformation`、权限调整等声明。因此，README 对原生 API 的概括不能替代逐项核对接口、信息类、权限和失败行为。本次只确认声明及公开功能描述，未逐项验证运行时清理效果。

如果以后涉及逐进程清理，排除名单必须按可靠身份匹配，处理进程退出和 PID 复用；仅提供可编辑的进程名称列表不足以证明操作范围可靠。

### 4. AF 已有能力与缺口

当前 `MemoryPruneCoordinator`、`ProcessMemoryTrimmer` 和资源参与者已经处理自身缓存、空闲、关屏、锁屏、睡眠及恢复。温和路径不交还工作集；深度路径执行托管回收并尝试交还当前进程工作集。按需回收已有节流和重入保护，应用页已有手动入口。

歌词缓存已经结合条数和估算字节预算，不能再把“增加缓存容量上限”笼统当成尚未实现的优化。下一步应根据采样找仍然保留的资源，并检查窗口、提供器和缓存的真实所有者。

建议顺序：

1. **自身诊断，复杂度低至中**：统一呈现工作集、私有内存、托管堆及最近回收原因/前后读数；明确这些读数采样时刻不同，不能相加当作总内存。
2. **自身手动控制，复杂度低至中**：复用现有协调器提供温和/深度选择，显示忙碌与失败结果；不新建第二条 GC 或工作集回收管线。
3. **手动系统实验，复杂度中至高**：单独的受限提权执行端，只接受固定清理项目，结果返回逐项状态；普通媒体栏继续非管理员运行。不开启常驻提权、自启任务或自动下载第三方程序。
4. **自动系统清理，复杂度高**：只有手动操作证明有效后再设计阈值、持续时长、回差、冷却、取消和低负载时机；不能仅因单次内存占用比例高就持续清理。

系统操作需要先讨论提权执行端的启动、调用验证、协议、退出和打包。普通 UI 线程不等待清理；用户取消 UAC、权限不足、接口不支持或部分项目失败必须有准确结果。

### 5. 评估方法

比较同一台机器、相同曲目/歌词/频谱、相近后台负载下的启动、稳定播放、关闭设置、空闲及恢复。分别记录工作集、提交、托管堆、CPU、缺页、磁盘活动和恢复交互耗时；需要时用 RAMMap 辅助判断缓存类别。

既看即时变化，也看恢复使用后的回升；记录无变化和负收益。系统总可用内存差值会受其他程序影响，界面应称“操作前后观测变化”，不能直接标成该操作精确释放的字节数。

## 二、PeriTray 可借鉴功能

### 1. 项目定位与本项目差异

[PeriTray](https://github.com/oneday5799/PeriTray/blob/aee4ea69a1019431138bc312f447222fd82d6a5e/README.md)覆盖音频、USB、蓝牙、显示器和无线外设。AF 的重点仍是媒体栏及音频交互，不宜直接扩展成完整外设管理器。

AF 当前音频实验已有输入/输出切换、黑名单、通信角色选项、前台应用目标、应用音量和路由反馈；这些不能再次作为全新能力重复建设。设备身份继续以端点标识为准，显示名不应成为切换依据。

| 候选能力 | 与 AF 的差异 | 收益与成本 | 建议 |
|---|---|---|---|
| 设备别名 | 目前主要使用系统名称 | 解决相似设备名和长名称；低至中 | 首批候选，只改 AF 展示，不自动重命名系统设备 |
| 收藏与自定义顺序 | 黑名单已有，常用集合和自定义顺序仍缺 | 缩小菜单与循环范围；低至中 | 首批候选，保留未收藏设备的可访问入口 |
| 指定设备快捷键 | 现有鼠标交互不能替代键盘调用 | 无需打开菜单；中 | 首批候选，默认不占用快捷键 |
| 常用设备循环快捷键 | 可复用现有切换服务 | 在耳机/音箱等集合快速切换；中 | 首批候选，跳过离线/黑名单设备 |
| 自定义分组 | 当前输入、输出分类已存在 | 多设备用户受益，配置面会增大；中 | 先验证收藏是否足够，再加分组 |
| 静音锁定 | 与 AF 调高音量解除静音语义不同 | 避免意外出声，但影响多个入口；中 | 后置，必须单独确认语义 |
| 耳机电量与低电量通知 | 尚无物理设备与电量通道 | 与当前输出设备相关；高 | 第二期，先标准系统路径和实际耳机 |
| 蓝牙连接/断开 | 不等于切换默认音频端点 | 可能减少系统设置跳转；高 | 单独评估超时、取消及失败反馈 |
| 2.4G HID 电量 | 需要厂商私有协议 | 部分型号实用；高且持续维护 | 暂不进入首批，不能按品牌宣称全面支持 |

### 2. 快捷键与设备身份的实现启示

[快捷键源码](https://github.com/oneday5799/PeriTray/blob/aee4ea69a1019431138bc312f447222fd82d6a5e/src-tauri/src/shortcut.rs)处理多个设备共享同一组合键循环，并保存注册失败结果供界面读取。借鉴重点是冲突可见、配置更新时注销旧键、只对当前可用设备操作，而不是默认安装一组全局快捷键。

若在 AF 落地，应由应用级输入服务管理注册与释放，窗口只表达配置意图；调用现有音频切换协调器，继续执行黑名单、通信角色及结果反馈。重复按键不能使迟到操作覆盖最新目标。

[设备身份源码](https://github.com/oneday5799/PeriTray/blob/aee4ea69a1019431138bc312f447222fd82d6a5e/src-tauri/src/device_identity.rs)使用设备容器等身份关联不同采集路径。[音频枚举](https://github.com/oneday5799/PeriTray/blob/aee4ea69a1019431138bc312f447222fd82d6a5e/src-tauri/src/audio.rs)也携带物理设备关联信息。这说明电量与音频端点关联应明确建模；不能只凭耳机显示名称相近就合并，也不能混淆同名设备。

别名、收藏与顺序应绑定稳定端点标识；设备重新配对导致标识变化时，需要保留失联条目供用户重新关联，不能悄悄把设置套用到另一台同名设备。物理设备电量关联另用容器或系统设备身份处理。

### 3. 电量、蓝牙及通知的维护边界

[蓝牙源码](https://github.com/oneday5799/PeriTray/blob/aee4ea69a1019431138bc312f447222fd82d6a5e/src-tauri/src/bluetooth.rs)包含不同蓝牙路径、缓存及状态操作。设备休眠、断开、驱动不提供电量时，界面应显示未知或最后更新时间，不能用 0% 代替读取失败。

[低电量通知](https://github.com/oneday5799/PeriTray/blob/aee4ea69a1019431138bc312f447222fd82d6a5e/src-tauri/src/battery_notify.rs)包含按阈值去重及电量回升后的重新启用。AF 若采用，应按设备身份与阈值去重，有明确回差和用户开关；不能每次刷新、连接或打开菜单都弹通知。

2.4G 设备依赖接收器和协议族。上游 README 明确并非全部列出型号都经过实测，因此仅能作为实现线索。新增协议需实际设备、维护负责人和不会干扰输入的验证，不能在媒体栏 UI 线程查询 HID。

### 4. 后续落地与验收建议

首批仅考虑“别名/收藏排序”和“设备快捷键”两组，分别作为可独立关闭的实验；不与耳机电量一起做跨模块重构。新增设置需要登记发布状态，沿用当前音频服务和本地化体系。

真机验证至少覆盖同名端点、USB 拔插、蓝牙休眠恢复、默认设备被系统改回、快捷键被其他程序占用、快速连按、停用实验与退出注销。电量功能另按真实耳机型号记录系统、驱动、连接方式和数据更新时间。

使用 computer-use 的 `@oai/sky` 初始化桌面工具并枚举窗口。工具的首次启动解析命中已安装实例，随后结束该次实例，使用准确文件路径启动本次 Release 构建并确认进程路径。

| 设置页场景 | 实际结果 |
|---|---|
| 导航至实验性功能 | 显示新增入口分组、说明及默认关闭的开关 |
| 开启外侧入口实验 | 显示打开方式，默认为“点击打开” |
| 打开方式下拉框 | 显示“点击打开”和“悬停 0.5 秒”两个选项 |
| 选择悬停方式 | 界面更新，配置文件保存为开启实验及 `Hover` |
| 关闭后重新开启实验 | 关闭时隐藏专属选项；重新开启仍保留悬停方式 |

用户随后明确将横杠实际操作验收留到下次，因此停止进一步操作。**设置页验证不代表横杠或自动隐藏体验已通过**；托盘正常退出与资源清理也未验收。测试实例已结束，原设置文件及其备份均通过字节哈希核对恢复；未改变 Windows 自动隐藏设置。

以下场景均为**待维护者验收**：

- 点击打开、横杠内悬停 0.5 秒、快速进入/离开及跨越过渡区域。
- 任务栏自然自动隐藏时保留入口，面板使用冻结锚点打开，离开后无残留命中。
- 普通媒体点击不会当成拖动隐藏入口；真正拖动、打开菜单及关闭实验会结束入口。
- 关闭面板后不自动重开；启用/关闭悬停层、入口开关及悬浮模式时行为正确。
- 上下左右任务栏、多屏混合 DPI、Explorer 重建、锁屏/睡眠恢复。
- 正常托盘退出后计时器、窗口及订阅均释放，反复开闭和重建不累积资源。

功能实现完成，当前状态为**待维护者验收**。内存与 PeriTray 扩展仍停留在本报告的调研与候选建议阶段。

## 五、内存与设备扩展的后续实施

后续以 `51099af` 为开发起点，已实现自身诊断及温和/深度回收、手动低优先级待机页清理、设备别名/收藏排序、系统设备快捷键，以及基于系统属性和标准 BLE 的电量展示与可选低电量提醒。所有新增实验默认关闭，没有引入自动系统清理、其他进程清理、蓝牙连接控制或厂商 HID 协议。
